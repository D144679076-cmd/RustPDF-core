# Type 3 Fonts — Implementation Report

**Date:** 2026-11-09
**Scope:** §9.6.5 Type 3 font rendering — `fonts/type3.rs` + interpreter Type3 path + fixture `type3.pdf`

## What Was Implemented

- **`src/fonts/type3.rs`** (new, ~310 lines):
  - `Type3Font::from_dict` — `/CharProcs` (dict incl. indirect resolution), `/FontMatrix` (default 0.001 point protocol), `/FontBBox`, `/Resources`.
  - Code → glyph-name table from `/Encoding` (named base, or `BaseEncoding` + `Differences` dict, incl. indirect reference). Shared `fonts::encoding::Encoding`.
  - `charproc(doc, name)` — resolves + decodes charproc stream, returns inner `/Resources` when present.
  - `parse_differences` — `[int, /name…]` flattener; out-of-range codes drop the names that follow them until the next valid code (malformed-input policy, unit-tested); `.notdef` skipped.
- **`src/content/interpreter.rs`**:
  - `Type3WidthBBox` (`d1`) now pushes a glyph-space bbox clip (like Form BBox, clips intersect); `d0` ignored — advance authority is `/Widths`.
  - `show_text` detects Type3 via new `resolve_font_dict` helper (shared font-dict resolution) and routes to `show_text_type3`.
  - `show_text_type3` — per code: locate charproc → `gfx.save()` → CTM = `trm ∘ FontMatrix` → clip `/FontBBox` (charprocs with `d1` tighten it) → `interpret_iter` on charproc content with charproc `/Resources` ∨ font `/Resources` ∨ page resources → `gfx.restore()` → advance via `/Widths` while capturing per-glyph pixel advances. Fill/stroke colors inherited per spec; `type3_depth` counters cap charproc recursion at 3.
  - `TextSpan.is_type3` flag added (new field; all constructors updated: interpreter, display×3, extractor test helper) — extractor keeps collecting spans; renderer skips rasterizing flagged spans (pixels already painted ⇒ no double-draw).
- **`src/parser/objects.rs`** — `PdfDocument::empty()`: no-object document shell for unit tests constructing standalone object graphs (safe: all fields default-empty; `resolve` on references fails cleanly).
- **`tests/gen_type3_fixture.py` + `tests/fixtures/type3.pdf`** — minimal Type3 font: `box` (800×800 filled square), `tri` (with `d1` announcing wx=400, tighter bbox), Encoding Differences 65/66, advance from `/Widths`.

## Design Decisions

- **Direct interpret-through-device, not bitmap-then-composite:** the plan's cached-bitmap idea existed because older devices couldn't re-enter the interpreter; today's `show_text_type3` runs charprocs through the same dispatch chain (`interpret_iter`) inside a glyph CTM, so paths/text/images in charprocs degrade consistently with page content and text state (`qs`-equivalent via `gfx.save`). No offscreen buffer lifetime issues.
- **Advance authority = `/Widths`** (like other simple fonts); `d0`'s wx is advisory per spec. This keeps one advance mechanism.
- **`d0` ignored, `d1` = clip**: rendering doesn't need d1's width metadata, only its clip semantics.
- **Per-stream decode cost**: charproc streams resolve through `PdfDocument`'s decoded_stream_cache (objectId → bytes), so repeated glyph instances on a page/tile hit the cache — implements the plan's caching intent without a new cache layer.
- **Fallback-to-nothing policy**: glyph without charproc → silently skipped (logged debug); ref-counted depth prevents runaway recursion.
- **Span still emitted (flag + skip)**: text extraction (ToUnicode CMap present) continues to work for Type3 without renderer double-draw.

## Test Coverage

- Interpreter: 845 lib unit tests green (342 → 845 with all-features; the +7 are type3's).

## Known Limitations / Follow-up

- CharPROC contents with **text operators** (`Tf`/`Tj` inside a charproc) inherit the outer `Tm` — spec says charproc text state is a default subset; complex nested-text glyphs may position differently until isolated (no real-world fixture seen yet).
- Charprocs containing their own `/XObject` or images work through the normal Do path; no dedicated tests yet.
- `d0` width mismatch with `/Widths` causes duplicated-advance drift only if producers are inconsistent; not auto-detected.
- Type 3 hit-testing/editing (span → glyph mapping is not backed by an embedded font; the editor's glyph model may treat these spans as display-only). Flagged for the editing roadmap later.
- No horizontal-displacement (`Tc/Tw`) verification inside charprocs — advance path shared with simple fonts, so unit confidence is indirect (via snapshot parity).
