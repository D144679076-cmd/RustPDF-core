# PDF 2.0 Phase E — Writer PDF 2.0 Emission (Opt-in) — Implementation Report

**Date:** 2026-11-07
**Scope:** PDF 2.0 support, Phase E of `pdf2-support-plan-2026-11-07.md` (writer side)

## What Was Implemented

**`src/writer/document.rs`** (extended):

- `EmitVersion` enum — `V1_7` (default) / `V2_0`. `V1_7` output stays byte-identical for every existing caller, test, and golden expectation; `V2_0` opts into the ISO 32000-2 emission policy.
- `PdfWriter::set_emit_version()` / `emit_version()` — opt-in + getter. Event-time normalization, not a write-time surprise.
- `PDF_HEADER_2_0` — `%PDF-2.0` header constant with the same binary-comment convention (§7.5.2/§7.2).
- `serialize_all` pre-pass `apply_pdf2_policy(root_id)` when `V2_0`:
  - **RC4 reject**: any pool dict with `/Filter /Standard`, `V ≤ 3`, `R < 5` (RC4-era Standard handler) → `Err(PdfError::WriteError)`. Never silently downgraded or written — ISO 32000-2 removed RC4.
  - **Catalog `/Version`**: defaulted to `2.0` when absent; caller-set non-2.0 version is left untouched with `log::warn!` (writer doesn't fight the caller).
  - **`/UF` autofill**: every `/Type /Filespec` missing `/UF` gets it copied from `/F` (Table 42: `/UF` required in 2.0 files) with a warning; Filespec with neither `/F` nor `/UF` fails closed (`WriteError`) — cannot autofill a required key from nothing.
  - Helpers: `obj_dict_of` / `obj_dict_of_mut` (dict + stream-dict borrows), `dict_is_rc4_encrypt` (detection predicate).
- Header selection at `prev_xref_offset.is_none()` — incremental updates carry no header (base file has one) but still get pool-level normalization, so an incremental update to a document is consistent with the policy without touching the base bytes.

**Cross-phase consistency:** reader-side policy gate (`crypto/handler.rs` Phase B) rejects RC4 in files claiming 2.0+; writer-side `apply_pdf2_policy` now makes producing such a file impossible through this crate. `pdf2_filespec_gets_uf_autofilled` round-trips through `Catalog::associated_files` (Phase C) to prove the autofilled `/UF` is real reader-visible data.

## Design Decisions

- **Default `V1_7`**: one `set_emit_version` call is the whole migration story; zero existing callers see new bytes. Matches the dual-version policy — support both formats, never surprise the caller.
- **Policy as serialize-time pre-pass**, not per-add-object checks: the whole document is consistent at serialization (e.g. a Filespec added *before* opting into V2_0 still gets `/UF`).
- **Fail closed** on unfixable violations (RC4 present, Filespec with no name at all): `WriteError` beats a malformed 2.0 file. Warnings (not errors) where the value is decidable (autofill from `/F`, caller-set stale `/Version`).
- **RC4 detection shape** is the V/R pair, matching the reader gate exactly — V≤4 is AES-128 (legal in 2.0), V=5/6 is the R5/R6 AES-256 class.

## Test Coverage

5 new tests (all happy + error paths, in `writer::document::tests`):

1. `pdf2_optin_emits_2_0_header_and_version` — V2_0 header bytes, `doc.version() == V2_0` after round-trip (Phase A reader), catalog `/Version 2.0` defaulted.
2. `default_writer_stays_1_7` — no opt-in → `%PDF-1.7`, no injected catalog `/Version`.
3. `pdf2_filespec_gets_uf_autofilled` — manual `/F`-only Filespec; round-trip asserts `FileSpec::name_uf` resolves through the Phase C reader.
4. `pdf2_rc4_encrypt_object_rejected` — synthetic RC4 `/Encrypt` dict in pool → `WriteError`; AES-128 (V=4/R=4) counterpart passes and emits a valid 2.0 file.
5. `pdf2_filespec_without_f_or_uf_is_write_error` — fail-closed path.

## Known Limitations / Follow-up

- `save_new` still never re-encrypts or carries `/Encrypt` forward (pre-existing TODO in `editor/document_editor.rs`) — RC4 rejection covers the pool layer; trailer-level encryption policy lands with that TODO's resolution.
- OCSP/CRL cryptographic validation and DSS write support remain deferred (plan §7) — readers only; writer emits no `/DSS` yet.
- Future-version policy (`%PDF-2.7`+ → warn + parse) is Phase A behavior; writer never emits a version above 2.0.
