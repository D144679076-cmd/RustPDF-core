# PDF 2.0 Phase B — Unicode Passwords + Encryption Policy — Implementation Report

**Date:** 2026-11-07
**Scope:** PDF 2.0 support, Phase B of `pdf2-support-plan-2026-11-07.md`

## What Was Implemented

- **`src/crypto/password.rs`** (new, ~240 lines incl. tests):
  - `decode_to_string()` — password text-string decoding in spec order (§7.6.4.3.2 / §7.9.2.2): UTF-16BE BOM → UTF-8 BOM → bare valid UTF-8 → PDFDocEncoding fallback (reuses `document/text_string::decode_pdf_text_string`, same documented Latin-1 approximation).
  - `saslprep_mapping()` — RFC 3454 mapping step (RFC 4013 profile): commonly-mapped-to-nothing codepoints removed (U+00AD soft hyphen, U+034F, U+1806/180B-E, U+200B-200F, U+2060-2064, U+FE00-FE0F, U+FEFF); non-ASCII spaces (U+00A0, U+1680, U+2000-200D, U+2028/2029/202F/205F/3000) mapped to U+0020.
  - `password_candidates_for_r6()` — `[normalised, raw]` (deduplicated: ASCII yields one candidate) in precedence order.
  - `normalize_password()` — named writer-side hook for Phase E.
- **`src/crypto/aes256.rs`**:
  - `verify_user_password_r6` / `derive_file_key_r6` now try all R6 password candidates through Algorithm 2.B (verify: `.any()`; derive: verify per candidate then derive with the winning candidate). R5 deliberately kept raw-bytes-only (pre-32000-2 extension path, no Unicode password semantics).
- **`src/crypto/handler.rs`**:
  - `EncryptionHandler::from_trailer(trailer, doc_id, password, version: PdfVersion)` — signature extended (Phase A version now flows to crypto).
  - **Encryption policy gate**: RC4 (V≤3, R<5) in a file claiming PDF 2.0-or-later → `log::warn!` + `Err(PdfError::Encrypted)` (graceful per R1/dual-version policy table). R5 in a PDF 2.0 file → warn only + kept parseable (Adobe Acrobat-IX AESV3 extension files share the shape).
- **`src/parser/objects.rs`**: production call site updated to pass `version`.

## Design Decisions

- **Candidates, not replacement**: R6 verification tries *normalised* first (PDF 2.0 semantic) then *raw* — ASCII passwords are bit-identical in both paths (single candidate, no double Algorithm 2.B cost), legacy extension-era R6 files hashed raw bytes. Mirrors Acrobat's observed tolerance behavior.
- **Mapping step only, no NFKC**: full SASLprep requires a Unicode-normalisation crate (`unicode-normalization`, WASM-safe but a new dependency). Byte-compatible results for ASCII and all passwords without decomposition-equal forms — the practical subset. Documented as follow-up; implemented crate-free to keep the dep tree unchanged (R2).
- **PDFDocEncoding table not duplicated**: password fallback reuses `text_string::decode_pdf_text_string` (Latin-1 approximation, consistent with the rest of the codebase) — a full Annex D.2 table is only needed if a real-world file proves the approximation wrong; the raw-bytes candidate covers that file anyway.
- **RC4 policy = hard reject in 2.0, keep in 1.x**: ISO 32000-2 removes RC4; but v1.x RC4 files remain ubiquitous. Gate lives in `from_trailer` so both `parse()` paths get it. R5 downgraded to warn-only (deprecated, not realistically malicious).

## Test Coverage

`crypto::password` (17 tests): ASCII passthrough, empty, UTF-8 BOM strip, UTF-16BE decode, bare UTF-8, soft-hyphen/zero-width/variation-selector removal, NBSP/em-space mapping, Latin-1 fallback (invalid UTF-8), two-candidate matrix for non-ASCII, single candidate for ASCII, truncated-UTF-16 lossy-decode no-panic.

`crypto::handler::tests` (3 new): RC4 V/R combos (2/3, 1/2, 3/3) rejected in PDF 2.0 files; RC4 still accepted in v1.4 files (R3 derivation runs); V5/R6 in PDF 2.0 file passes through R6 derivation (wrong password → `Encrypted` from R6 path, not the gate).

Regression: all pre-existing AES-256/R5/RC4 tests pass unchanged (403 total with `--features crypto`).

## Known Limitations / Follow-up

- SASLprep NFKC normalisation step not implemented (needs `unicode-normalization` dep — defer until a real-world non-ASCII password file demands it).
- Full RFC 3454 prohibited/output tables not implemented (passwords are free-form; spec's intent is interop, not validation).
- R6 *writer-side* password setting (creating R6 dicts with hashed Unicode passwords) — Phase E.
- Policy gate reads V/R from passed version only for encryption; `/Encrypt` indirect-ref resolution unchanged.
