# PDF 2.0 Phase D — Document Security Store (DSS/LTV) — Implementation Report

**Date:** 2026-11-07
**Scope:** PDF 2.0 support, Phase D of `pdf2-support-plan-2026-11-07.md` (read-only parse)

## What Was Implemented

**`src/signatures/dss.rs`** (new, feature-gated with `signatures`, ~300 lines incl. tests):

- `DssPayload` — `Reference { id }` (lazy) vs `Inline { der }` (direct stream in an array).
- `DssItem` — one DER blob entry; `.der(doc)` resolves lazy refs through **`PdfDocument::get_stream_data`** (filter + per-object encryption applied automatically) and returns plain DER bytes.
- `VriInfo` — per-signature `/VRI` entry: hex signature-hash key (verbatim), `cert_refs` / `ocsp_refs` / `crl_refs` arrays, single `ts_ref` (RFC 3161 time-stamp — spec-defined as one stream, *not* an array).
- `DocumentSecurityStore` — pooled `/Certs`, `/OCSPs`, `/CRLs` + `vri` list.
- `parse_dss(doc, catalog_dict) -> Result<Option<DocumentSecurityStore>>` — `None` when `/DSS` absent (the default), typed `Err(PdfError::InvalidStructure)` when `/DSS` or pool arrays have the wrong type.

Wiring: `signatures/mod.rs` re-exports `parse_dss, DssItem, DssPayload, DocumentSecurityStore, VriInfo`.

## Design Decisions

- **Laziness is the headline**: real LTV documents carry multi-MB CRL pools. Pool entries stay `Reference { id }`; `.der()` is the only inflation point — callers (future OCSP/CRL validation phase) fetch only the material they'd trust.
- **Resolve-before-inspect bug caught by tests**: first implementation resolved every array item *then* matched on the resolved type — `resolve()` follows reference chains to their targets, so `Reference { id }` arm was unreachable, laziness was silently lost, and (worse) an object identity leak: `.der()` on an inline payload returned `raw_data` without the decrypt/filter pipeline. Fix: inspect the **pre-resolve** object; only non-reference entries resolve (rare inline streams).
- **`/TS` ≠ array**: spec §12.8.4 `/VRI → /TS` is a single stream; running it through the pool-array parser produced the "not an array" error — grouped with the pre-resolve fix.
- **Strictness contract**: absent `/DSS` = `Ok(None)` (open path unaffected); wrong *types* (array where dict required etc.) = `Err` — callers that must never fail the open path degrade themselves. Matches the plan's "never fail document open, but expose enough types for a structured verifier".
- **Unknown `/VRI` keys / non-stream pool entries** skip with `log::warn` — revocation pools are rewritten per incremental update; partial junk is a real-world constant.

## Test Coverage

8 tests:
- Happy: pools + VRI parsed; laziness asserted (`payload == Reference { id: 4 }`); `.der()` decodes all four kinds (pool cert, pool OCSP, pool CRL, VRI `TS`).
- Degradation: no `/DSS` → `None`; `/DSS` non-dict → `Err`; pool non-array → `Err`; bad VRI entry skipped while good ones kept; absent pool keys + empty `/VRI` → empty store.
- Inline-stream pool entries are covered by code path but not yet by a fixture (bare `stream` token can't appear inside an array literal in our crafted-byte fixtures — real-world LTV fixture in Phase F).

## Known Limitations / Follow-up

- OCSP/CRL cryptographic **validation** — deferred to its own phase (plan §7); this module only surfaces material. Hook point: extend `verify_signatures` to call `parse_dss` and pass `.der()` bytes as revocation material to the CMS verifier.
- VRI hash verification (that the hex key actually equals SHA-1 of the signature `/Contents`) — validation-phase work.
- Inline-stream pool fixture — Phase F real PDF.
- Writer-side DSS emission (updating an LTV document must preserve/extend `/DSS`) — Phase E scope.
